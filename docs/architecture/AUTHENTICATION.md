# Staff authentication and bootstrap

Date: 2026-10-14. Scope: Phase 04. Source: the complete Phase 04 prompt, SEC-001–004, DAT-005 and REL-003/007/008. Implementation evidence is in the Phase 04 verification ledger; this document does not qualify native packaging or deployed HTTPS.

## Identity and instance ownership

Each migrated empty database receives one randomly generated `auth_installation.instance_id` and a persistent `new` state. Migration examines every pre-existing cv table as the forced-RLS guard; a populated or damaged predecessor database receives `closed`. It does not silently adopt old fixture accounts. The migration leaves all predecessor business values intact. A missing installation row is unavailable, never interpreted as new.

The explicit operator configures the database's local/server kind, realm key, immutable authentication policy and generated transient startup authority. A configured new installation may rotate startup authority only with the same kind/key/policy. The local API admits startup instance/proof/state/expiry under this singleton lock before hashing any password. Bootstrap repeats the checks after hashing, verifies the empty agency set, then inserts the agency/admin identity/membership/audit and consumes startup authority in one transaction. A second or concurrent bootstrap loses the race. Deactivation, password failure, missing membership or lost password cannot set the installation back to new.

Staff identities have user-chosen lowercase login names and passwords. Login names use the explicit ASCII identifier grammar in the generated schema; display/person names are separate domain data. Passwords permit spaces and valid Unicode, reject unencodable lone surrogates and control characters, and follow validated length policy. Shared password DTO validation returns safe422 errors before hashing. Hash/verify and operator validation also enforce Unicode safety. Relevant free-text identity/policy inputs reject invalid Unicode before database encoding. Argon2id salts are generated by argon2-cffi. The synthetic authentication policy explicitly selects memory/time/parallelism, bounded hash concurrency and wait time. The library's recommended Argon2id mechanism was checked in [official documentation](https://argon2-cffi.readthedocs.io/en/stable/howto.html); no project speed or hardware claim follows from its example timings.

Sessions use independent random 256-bit bearer proofs and persist only SHA-256 proof digests. Startup proofs never become sessions. `auth_session` binds each new session to its instance. Login includes the instance UUID; the configured API verifies its database realm key/kind. A foreign instance token, legacy test proof, guessed tenant header or another database's credentials does not establish authority. Independently creating equal passwords in two databases does not transfer identity.

## Transactions and limits

The trusted Python service verifies passwords before calling the restricted session-creation function. It reads credential hashes only through the trusted runtime service database connection; they never enter API DTOs, public schemas or logs. Direct possession of a database service credential and hostile Python introspection are outside the API threat boundary, consistent with Phase 03's trusted-adapter contract. The public DB role cannot call any identity function or read staff tables. All new tables use forced RLS and the nonlogin guard; migration owner and runtime remain separate.

Login locks installation state, reserves a persistent global and account attempt, verifies Argon2id, creates session/audit and validates current authority before returning a token. Invalid attempts commit their counters before the API emits the generic denial. Admitted attempts for unknown and inactive accounts use a random non-account dummy hash and the same error envelope. Refused account/global reservations do not call Argon2, while preserving the same safe HTTP denial. A configured fixed window bounds distinct account counter rows through the global ceiling; old counters are removed when the global window rolls over. Counters persist across API restarts. Live-session capacity is enforced under the same lock; reaching it denies a new login instead of evicting another device. Expires/revokes free live capacity. This is a bounded single-agency design, not a measured scalability promise. Expired/revoked session and audit history is retained; production archival policy remains part of later retention/security qualification.

Authenticated operations bind a proof before current tenant/user/role exists. PostgreSQL uses backend PID plus transaction ID, so a new transaction cannot inherit old context. The production adapter opens bounded fresh connections rather than using a shared pool; tests also reuse one actual PostgreSQL connection across commit, rollback and invalid binding. All results are provisional until context exit completes. Current identity/member/session locks and a fresh-clock check run immediately before commit. Policy activation/grant additionally retains nonconsumable transaction-local obligations after early constraint checks and idempotent replay. Logout is a terminal command: validate authority, revoke the current session, remove its transaction context, then commit without caller work. This establishes authority at finalization, not continuously during subsequent WAL/network delivery.

Staff mutations require an idempotency UUID and store a keyed HMAC payload digest, response and audit in the same transaction. Password-containing retry payloads never create an unkeyed password dictionary oracle. A different payload with the same actor/operation/key is rejected. Staff update checks membership revision and revokes every session for the changed user. Self-role/deactivation changes are refused, preserving an active administrator. Policy history is immutable; revocation is a separate attributed record. Purpose grants have a separate revision guard. Domain reads still use current purpose/consent/scope RLS and finalization from Phase 03; authentication administration does not grant a standing recruitment purpose.

## Transport and session interfaces

The generated staff OpenAPI contains `/auth/v1/instance`, bootstrap/login/session/logout/revoke, `/staff/v1/users`, policies and purpose-grants. The generated public graph contains only public operations and no password/token/staff DTO. Every private response uses no-store and nosniff. Input validation emits a safe generic message without reproducing input values. Wrong password, nonexistent account, inactive identity and exhausted login allowance share `AUTH_DENIED`; callers cannot use a separate public account-existence route. Staff-only conflict responses are available only after authenticated administrator authority.

Bearer authorization is explicit; cookies are rejected on identity/staff routes and credentials are omitted by the typed client. State changes use JSON POST with explicit proof and idempotency where required; no cookie-based CSRF exemption is inferred from CORS. Development local browser origins are limited to the configured desktop and Tauri virtual origin. Public web cannot call staff routes with its origin. Server staff requests reject every browser Origin and require the native HTTPS transport. Server scope rejects HTTP even with a forged X-Forwarded-Proto header. Developer Uvicorn disables proxy-header trust. Owner 16 must configure any approved TLS termination without accepting untrusted forwarding assertions. ASGI HTTPS tests verify these code branches; approved deployed TLS/certificates/CORS remain UNVERIFIED owner 17.

`MemorySessionState` is an implemented development interface, not a UI. It binds immutable context to origin/instance/mode, rejects connected HTTP, stores the bearer only in memory, omits cookies, denies redirects and bounds fetch time. Generation tickets and abort signals discard stale completions after clear/logout/mode replacement. UI consumers must check ticket validity before adopting response bodies. Each mode gets a distinct state object; no fallback endpoint or automatic synchronization exists. Browser refresh loses the session. Pending logout must clear local state immediately and report network uncertainty rather than claim server revocation succeeded.

Phase 15 must implement native storage keyed by application identity, device, local workspace/server instance and approved origin. Its interface is `load(scope)`, `save(scope, session)`, `remove(scope)` and `clearActiveScope()`. A load never establishes authority: the API must validate current session before protected views. Portable database accounts travel with the data; Credential Manager entries and device-session authority do not authorize a copied workspace on a new machine. Device binding and actual keyring tests remain UNVERIFIED owner 15. Phase 04 provides no simulated keyring and no persistence in localStorage, IndexedDB or browser bundles.

## Password loss and recovery limits

There is no default password, anonymous reset, recovery question or operator login bypass. An authenticated admin can create another authorized user; changing another existing user's password is not implemented here. If every administrator password is lost, app-level recovery is unavailable. Preserve the workspace and follow the future authorized backup/recovery design; do not delete identity rows or reopen bootstrap. A deliberate fresh workspace has distinct data and identity and does not recover the old one. OS administrator or physical database copy is outside application access protection; no whole-disk encryption, copy resistance or certification is claimed.

## Development operator path

Use a separately created empty, migrated development database and the operator's approved central settings. Never point this workflow at the populated Phase 03 test database, which correctly stays closed to bootstrap. The `database_secret_env` in settings points to validated runtime connection JSON using `cv_runtime`. The operator passes a different environment-variable name containing the same validated endpoint fields with `user=cv_migrator` and its secret. Both are process environment references, not committed secrets or browser config. All endpoints/timeouts/paths come from central settings.

Run `.venv\Scripts\python.exe -m cv_api.operator --config <settings-file> --profile development --operator-secret-env <operator-env-name> --agency <chosen-agency-name> --login <chosen-login>`. The CLI reads and confirms the password with `getpass`, generates transient startup proof in memory, configures and creates the real admin in one PostgreSQL transaction, then prints only a safe success status. No startup token/password is printed or written to disk. Launch the development API with its existing explicit config/profile command; read the instance descriptor and log in through the generated staff API. A server operator uses `--profile server` and a server-owned policy/settings; no web bootstrap is exposed. Recipient zero-setup native launch remains Phase 15/17.

The test calls the real CLI entrypoint with only terminal prompting substituted, then uses a real Uvicorn socket and real PostgreSQL to authenticate/revoke. It does not qualify an interactive Windows first-launch screen. Authentication settings are required and validated even in schema/test construction. `authentication-test.json` is explicitly synthetic policy, not production approval; policy values must match the configured installation rather than changing silently on restart.
